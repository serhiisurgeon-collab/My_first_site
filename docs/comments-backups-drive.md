# Ручні приватні копії: Google Drive, 30 діб

Погоджено власником: приватна папка Google Drive без спільного доступу; копія зберігається **30 діб від часу створення експорту**, а не від завантаження чи шифрування. Автоматичної інтеграції/ротації/видалення немає. Нижче — процедура для налаштування й перевірки; її ще не виконано на комп’ютері/Drive власника. До цього політика не описує шифрування та Drive як уже діючий порядок.

## Один раз перед використанням

1. У своєму Google Drive створити папку `Comments backups — private`. «Поділитися» → «Загальний доступ»: **Обмежений**. У списку доступу — лише ваш акаунт, без інших учасників/груп і без успадкованого спільного доступу. Не використовувати спільний диск або загальнодоступне посилання. Налаштування доступу перевірити також після завантаження першої копії.
2. Встановити актуальну версію 7-Zip з офіційного https://www.7-zip.org/ на Windows, якщо її ще немає. Не завантажувати інсталятор із випадкового дзеркала.
3. Локальна робоча папка — поза репозиторієм/сайтом, наприклад `D:\Private\CommentsBackups\`. Вона не має бути папкою автоматичної синхронізації Drive/OneDrive: незашифровані JSON не повинні завантажуватися самі.
4. Створити довгу випадкову парольну фразу в менеджері паролів; зберігати її окремо від архівів, не в цій Drive-папці, не в Git/чаті/командному рядку. Без неї відновлення неможливе. Погоджені локальні резервні способи зберігання пароля не називаємо вже налаштованими.

## Кожен ручний експорт

1. Перед плановою міграцією/очищенням або іншою погодженою зміною призупинити надсилання (`enabled:false`) й сторонню модерацію/Console-зміни. Створення цієї копії саме по собі не є дозволом виконати міграцію чи видалення.
2. У знайомій панелі адміністратора натиснути **«Експортувати приватну JSON-копію»**. Використовувати штатний exporter і його тимчасовий замок. Дочекатися повного файла; при обриві не вважати файл завершеним. Перевірити unlocked control й `enabled:false`. Чужий замок не знімати.
3. Зберегти JSON у приватній локальній папці. Зберегти manifest із форматом, projectId, часом, кількостями та SHA-256; звірити hash файла. Долучити актуальний deletion register з наявною історією, а не створювати порожній замість попереднього. Нова копія після privacy-міграції має формат v3 із commentOwners; до міграції дозволено перевірений legacy v2 з подальшою конвертацією при restore.
4. Оновлення реєстру з попереднім регістром, якщо потрібне:

```powershell
node tools/comments/recovery-files.mjs register 'D:\Private\CommentsBackups\fresh.json' 'D:\Private\CommentsBackups\register-new.json' 'D:\Private\CommentsBackups\register-current.json'
```

Імена output мають бути новими: інструмент не перезаписує файли. Поточний authoritative register — службові дані, що потрібні для suppression, а не одноразова історична копія. Зберігати його окремо приватно/зашифровано; старі версії всередині архівів видаляються разом із відповідним архівом через 30 діб. Його актуальність не замінюється очищенням старих архівів.

5. Записати час створення та точну дату видалення. У PowerShell:

```powershell
$backupPath = 'D:\Private\CommentsBackups\fresh.json'
$backupData = Get-Content -LiteralPath $backupPath -Raw -Encoding UTF8 | ConvertFrom-Json
$createdUtc = [DateTimeOffset]::Parse($backupData.exportedAt).ToUniversalTime()
$deleteAfterUtc = $createdUtc.AddDays(30)
$createdUtc.ToString('o')
$deleteAfterUtc.ToString('o')
$backupHash = (Get-FileHash -LiteralPath $backupPath -Algorithm SHA256).Hash.ToLowerInvariant()
$manifestPath = 'D:\Private\CommentsBackups\manifest-new.json'
if (Test-Path -LiteralPath $manifestPath) { throw 'Не перезаписуйте наявний manifest; оберіть нове ім’я' }
$manifest = [ordered]@{
    manifestVersion = 1
    backupSchemaVersion = $backupData.schemaVersion
    sourceProjectId = $backupData.projectId
    backupFile = [IO.Path]::GetFileName($backupPath)
    createdAtUtc = $createdUtc.ToString('o')
    deleteAfterUtc = $deleteAfterUtc.ToString('o')
    counts = $backupData.counts
    backupSha256 = $backupHash
}
$manifestJson = $manifest | ConvertTo-Json -Depth 10
[IO.File]::WriteAllText($manifestPath, $manifestJson, [Text.UTF8Encoding]::new($false))
$archiveName = 'comments-created-{0}-delete-{1}.7z' -f $createdUtc.ToString('yyyyMMddTHHmmssZ'), $deleteAfterUtc.ToString('yyyyMMddTHHmmssZ')
$archiveName
```

У приватному журналі: назва архіву, projectId, формат, createdAtUtc, **deleteAfterUtc**, SHA-256 архіву, перевірка restore і позначка ручного видалення. Журнал не має містити текстів/UID/паролів. Дату не переносити при повторному завантаженні чи перепакуванні.

## Шифрування без пароля в командному рядку

1. У 7-Zip File Manager виділити backup, manifest, актуальний register і короткий запис createdAtUtc/deleteAfterUtc.
2. «Add / Додати до архіву»: **7z**, шифрування **AES-256**, пароль із менеджера; ввімкнути **Encrypt file names / Шифрувати імена файлів**. Не використовувати звичайний незашифрований ZIP.
3. Назва без імен/UID, наприклад `comments-created-YYYYMMDDTHHMMSSZ-delete-YYYYMMDDTHHMMSSZ.7z`. Дата видалення з попереднього обчислення.
4. «Test / Тест» архіву з введенням пароля. Окремо розпакувати в іншу приватну локальну папку, повторно звірити SHA-256 кожного JSON із вихідним. Невірний пароль має відхилятися. Після першого налаштування й після зміни інструменту провести штатний restore саме розпакованої копії в новий порожній demo emulator із поточним register та full comparison. Це не відновлення Firebase Auth або всієї хмари.
5. SHA-256 архіву для журналу:

```powershell
Get-FileHash -LiteralPath 'D:\Private\CommentsBackups\YOUR-ARCHIVE.7z' -Algorithm SHA256
```

## Завантаження й контроль

1. Вручну завантажити **лише зашифрований .7z** у приватну Drive-папку. JSON/незашифрований manifest/register окремо не завантажувати.
2. Перевірити доступ: «Обмежений», тільки ваш акаунт. Завантажити архів назад у окрему приватну папку, звірити його SHA-256 із журналом, перевірити пароль і розпаковані JSON. Тільки після цього позначити цикл export→encrypt→upload→download→verify як перевірений.
3. Прибрати непотрібні незашифровані локальні робочі файли й тимчасове розпакування після успішної перевірки; залишити лише потрібні актуальні службові файли в погодженому захищеному місці. Це звичайне видалення файлів, не гарантія фізичного перезапису SSD або очищення системних snapshot/історії.
4. Поставити собі ручне нагадування на **deleteAfterUtc** кожної копії. Не покладатися лише на щомісячний перегляд: він може пропустити точний 30-денний строк. Якщо до закінчення строку останньої копії потрібен recovery — створити/перевірити нову; строк старої не продовжувати.

## Видалення через 30 діб

У зазначену дату вручну видалити архів із Drive, потім видалити цей самий архів із **Кошика Drive**, а також локальні/download/розпаковані дублікати. Перевірити приватний журнал і позначити час видалення. Не редагувати старий архів у Drive: це може залишити історичні версії, краще окремий новий файл з власною датою. Не стверджувати, що це очищає всі внутрішні технічні копії провайдера: їхній цикл визначає Google.

Актуальний deletion register не видаляти разом із останньою історичною копією: він потрібен для виключення повернення видалених даних та розгляду звернень. Строк його службового зберігання — окреме рішення. При запиті на видалення даних окремо переглянути всі ще не прострочені архіви; register запобігає restore, але не стирає дані всередині старого архіву.

## Що ще NOT RUN

Налаштування Drive/7-Zip/пароля на машині власника, повний цикл із завантаженням і поверненням, неправильний пароль, restore розшифрованого файла та ручне видалення тестового архіву. До їх перевірки не писати в політиці, що шифроване Drive-зберігання вже працює. Автоматичну інтеграцію чи автоматичне видалення не створено.
