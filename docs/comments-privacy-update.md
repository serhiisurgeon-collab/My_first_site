# Оновлення приватності коментарів — review/comments-privacy

Підготовлено від main `184615a4e93ac7a71114ff9b903405dff3a6801a`. Це локальна review-гілка. Наявний Firebase `serhii-comments-test`, Auth-акаунти, адміністратор і живий сайт не змінені. Конфігурація опублікованого main збережена; для review використовуйте лише локальний overlay на емулятори. Не відкривайте новий клієнт зі старими хмарними Rules: їхні схеми несумісні.

## Дані та права

- `comments/{існуючий ID}` schema3: schemaVersion, articleId, authorName, text, parentId, depth, status, createdAt, updatedAt. Публічне читання published/deleted без UID. Pending/hidden — відповідний автор або адміністратор. Публічний запит має schemaVersion==3, articleId, статус і limit<=20.
- `commentOwners/{той самий ID}`: authorUid, articleId, createdAt, confirmation. Читає лише цей автор або адміністратор; приватні запити автора фільтруються за його UID й обмежені 20. Зміна чи видалення клієнтом заборонені навіть адміністратору.
- `confirmation` нового запису: accepted:true, version, confirmedAt:serverTimestamp. Версія премодерації `comments-publication-2026-10-v1`; для наявного post-режиму є окремий точний текст/версія `comments-publication-post-2026-10-v1`. Повідомлення архівовано у publication.js. Це свідчення підтвердження публікації, а не згода на всю обробку. Старі записи мають confirmation:null.
- Створення — одна транзакція comments + commentOwners + rateLimits. Rules перевіряють автора, ім’я з Google token, серверні дати, позитивне підтвердження чинної версії, батька/статтю/глибину й 60 секунд. Немає окремого запису автора — весь запис відхиляється. Старі клієнти не можуть створити публічний UID.
- `articles/{a-0001..a-0004}` містять лише slug/aliases; `settings/comments` — лише дозволені поля schema1/2. Адміністратори, блокування, лічильники, аудит і control залишаються приватними. Невідомі шляхи заборонені. Firestore Rules перевіряють запит, а не приховують окремі поля відповіді: безпечна schema3 спирається на сувору форму створення/зміни та перевірену міграцію. Довірений Console/Admin SDK обходить Rules і може зіпсувати цей інваріант; тому кожен публічний документ/ID перевіряється перед запуском, і не можна просто додати schemaVersion:3 до старого запису з UID. Пряме get додатково перевіряє точні ключі. Жодної нової публічної колекції UID не створено.
- UA/EN використовують попередні спільні articleId. Модерація отримує UID з приватного запису. Видалення тексту не стирає авторство, підтвердження, Auth чи гілку; залишкові персональні дані не називаються анонімними.
- Auth налаштовано на browserSessionPersistence до входу/слухача. Оновлення сторінки зберігає вхід; нова вкладка після закриття не отримує його. Браузерне відновлення закритої сесії може повернути sessionStorage: на спільному пристрої потрібен явний вихід.

## Інвентар перед будь-якою хмарною зміною

Актуальний список хмарних записів **NOT RUN**: старі завантажені тестові копії не є поточним інвентарем. Не можна припускати, що живі записи тестові. До погодження нічого не мігрується і не видаляється.

Після окремого погодження зупинити нові надсилання (enabled:false) та сторонню модерацію/Console-зміни. Наявним опублікованим exporter створити свіжу приватну v2-копію, manifest і актуальний deletion register. Звірити завершеність, unlocked control і SHA-256. Файли поза сайтом і Git; не просити service account key.

У PowerShell від кореня review-коду:

```powershell
node tools/comments/privacy-migration.mjs 'D:\PRIVATE\fresh-backup.json'
```

Команда не підключається до Firebase. Виводить кожен `comments/ID` → `commentOwners/ID`, статус, причину, кількості, SHA-256 вихідного файла, окремий semantic source hash і hash плану. Без текстів/UID у звіті, але IDs/план теж зберігайте приватно. Показати цей точний список власнику перед хмарною міграцією. Offline-інструмент не має apply. Контрольований cloud runner з повторною звіркою й окремим погодженням — `cloud-privacy-migration.mjs`, порядок: comments-cloud-migration.md. Якщо знайдено UID у публічному ID, тексті, реєстрі чи інших полях — конвертація зупиняється; не перейменовувати ID й не переписувати текст самовільно.

Міграція має переносити UID атомарно для кожної пари, видаляти лише публічне authorUid, додавати schemaVersion:3 і приватний запис з confirmation:null. Зберегти ID, authorName/text, статус, createdAt/updatedAt з точними timestamp, parentId/depth і articleId. Ні pending, ні hidden не стають published. Зіставити кожен запис свіжого інвентаря з хмарою перед записом; розбіжність — зупинка. Для нових private-пар Rules навмисно не дозволяють заднім числом підтвердження; саму погоджену міграцію виконує власник контрольованим cloud runner із user ADC, а не звичайним Web SDK або ручним переносом кожної пари. Cloud apply підготовлено, але не запущено; порядок: comments-cloud-migration.md.

## Копії та відновлення

Новий exporter формує v3 із commentOwners, рештою попередніх колекцій, settings/control і article map. Штатний власний замок, повна пагінація, перевірка кількостей, відмова від часткового експорту та зняття лише власного замка збережені. Формат settings лишається schema2; deletion register — schema1.

Старі v1/v2 приймаються лише як приватний вхід. Після застосування актуального реєстру видалень restore обов’язково перетворює їх у v3; UID у публічні comments не записується, підтвердження лишається null. Орфанні private-пари, невірні зв’язки/дати, зайві поля або UID у публічних даних відхиляються. Оригінальна копія не змінюється. Старий register зберігається й нарощується, не створюється порожній замість відомих видалень.

```powershell
$env:FIRESTORE_EMULATOR_HOST='127.0.0.1:8080'
$env:COMMENTS_RESTORE_PROJECT='demo-privacy-restore-new'
npm run comments:restore -- 'D:\PRIVATE\fresh-backup.json' --deletion-register 'D:\PRIVATE\current-deletion-register.json'
# Лише після preview: новий порожній demo-* та effectiveSha256 зі звіту.
npm run comments:restore -- 'D:\PRIVATE\fresh-backup.json' --deletion-register 'D:\PRIVATE\current-deletion-register.json' --apply --confirm-emulator-restore --sha256 'EFFECTIVE_HASH_FROM_PREVIEW'
```

Без loopback endpoint, з непорожньою ціллю, пошкодженою копією, неправильним hash чи без register apply заборонено. Цей інструмент не відновлює реальну хмару чи Firebase Auth. Звірка — усі шляхи/ID/поля/типи/дати, а не лише кількість; допустима конвертація — authorUid→private, schema3, confirmation:null та suppression з register. Замок у копії має бути unlocked.

## Ручне очищення

`cleanup-plan.mjs` — лише offline dry-run, не містить Firestore/Auth client і ніколи не видаляє. `--apply` відхиляється. Строки не задані за замовчуванням. Після погодження потрібен окремий приватний JSON: approved:true, явний asOf (ISO дата), holds:[], та лише погоджені positive integer pendingDays / hiddenDays / rateLimitDays. emptyTombstoneDays приймається для пропозиції, але видалені tombstones автоматично не обираються: походження видалення й відповіді треба зберегти.

```powershell
node tools/comments/cleanup-plan.mjs 'D:\PRIVATE\fresh-backup.json' 'D:\PRIVATE\agreed-retention.json' 'D:\PRIVATE\current-deletion-register.json'
```

Вивід: точні кандидати/причина/кількість/hash. Published, батьки відповідей, tombstones, holds і пов’язані утримувані записи не обираються; Auth/admin/settings/control/articles/blocks не видаляються. Видалення коментаря не пропонується, якщо пов’язаний rateLimits ще не підпадає під явний строк. Перед будь-яким майбутнім apply потрібні новий експорт, актуальний register із suppression майбутніх видалень, звірка хмарного списку й окреме підтвердження кожного шляху. Вихід dry-run сам по собі не є дозволом видалення. Регулярний запуск, 30 днів, шифрування чи ротацію не запроваджено.

## Порядок застосування та відкат

Усі кроки нижче — майбутні, після окремих погоджень.

1. Дата політики й повідомлення — фактичний день спільної публікації, однаково UA/EN, без задньої дати. Погоджено приватну папку Google Drive і 30 діб від створення копії з ручною датою видалення; налаштувати й перевірити export→encrypt→upload→download→restore за comments-backups-drive.md. Інші строки очищення лишаються пропозицією: comments-retention-proposal.md.
2. enabled:false, пауза модерації, свіжі backup/manifest/register; точний інвентар та dry-run. Погодити конкретний міграційний список.
3. Додати нові індекси comments(articleId,schemaVersion,status,createdAt) та commentOwners(authorUid,articleId,createdAt), дочекатися Enabled. Старі індекси на першому етапі не видаляти: файл review зберігає обидва старі та додає два нові; видалення старих потребує окремого рішення.
4. Застосувати погоджені нові Rules. Старі публічні comments без schema3 стають недоступні публічно; адміністратор ще може зробити приватний inventory/export через старий клієнт. Очікувана коротка недоступність обговорення без впливу на статтю.
5. Виконати погоджену атомарну міграцію пар при disabled. Не змішувати клієнти старої/нової схеми. Звірити всі дані, UID-поля/ID, private-доступ, suppression; експорт v3 і full emulator restore comparison.
6. Після окремого дозволу опублікувати клієнт/політики/повідомлення разом. Прочитати settings із сервера; повернути visible, pre та enabled тільки до погодженого значення. Не створювати новий проєкт, Auth/IAM/billing не змінювати.

Відкат: насамперед enabled:false, за потреби приховати інтерфейс; статті залишаються доступні. Зберегти privacy Rules, приватні owner-документи та schema3. Не відкочувати до старих Rules/клієнта, які знову пишуть або відкривають UID; приховування UI цього не вирішує. Для recovery використати v3 або конвертовану копію з актуальним register, спершу ізольований restore й повну звірку. Відновлення хмарних даних також потребує окремого дозволу. До початку міграції локальний review можна просто відкласти — main і хмара не змінені.

## Що справді перевірити власнику

1. Текст політики й повідомлення UA/EN, дату чинності та строки/місце приватних копій.
2. Один реальний Google-вхід: reload у тій самій вкладці, явний вихід; окремо поведінку вашого браузера з функцією відновлення закритих вкладок. OAuth реального проєкту в цій роботі не повторювався.
3. Один новий коментар із явною галочкою після погодженої міграції; його pending і переклад використовують одну гілку. Решту прав і відновлення покривають автоматичні тести.

## Уточнення перед запуском

Cloud runner готовий для контрольованого dry-run/apply після окремих погоджень; див. comments-cloud-migration.md. Політика й технічне оновлення публікуються разом у фактичний день. Приватний Google Drive/30 діб погоджені, але шифрування й завантаження поки NOT RUN; їх не описувати як вже діючі заходи до перевірки.
