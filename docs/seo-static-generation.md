# Статичні статті: збірка, перевірка та додавання матеріалу

## Публікація залишається чинною

GitHub Pages використовує legacy/Jekyll із кореня `main`. Немає нових
GitHub Actions, дозволів, серверів чи сервісів. Згенеровані HTML, WebP,
`data/article-routes.json`, sitemap і robots зберігаються у Git.
Генерацію потрібно виконати **до** майбутнього погодженого коміту/push.
Jekyll сам генератор Node не запускає. Наразі push/merge/deploy не погоджені.

Джерела статей: `data/articles.json`, `data/articles-en.json`,
`content/articles/{uk,en}/*.md`, оригінальні мовні зображення та
`firebase/article-map.json`. Шаблони: `tools/seo/templates/`.
Не редагуйте згенеровані `articles/*/index.html` чи `en/articles/*/index.html`.
Основні сторінки також генеруються: для зміни їхнього дизайну редагуйте
відповідний файл `tools/seo/templates/pages/`, потім перезберіть.
Тексти головного блоку останніх матеріалів і картки статей беруться з JSON.
Це не дві незалежні ручні копії медичного тексту.

## Відтворювана перевірка

Node 24.19.0 використаний під час перевірки; залежності зафіксовані в
package-lock.json. Markdown: marked 15.0.12; санітизація: sanitize-html 2.17.0;
HTML: cheerio 1.0.0; lossless WebP: sharp 0.34.5. HTML-парсер не виконує
скриптів із Markdown, небезпечні URL-протоколи та обробники подій видаляються.

```powershell
cd D:\Trainer\my_first_site
npm ci
npm run seo:build
npm run seo:check
npm run seo:test
npm run seo:jekyll
npm run seo:public-check
$env:SEO_SITE_DIR = '.private/seo-jekyll'
npm run seo:test
Remove-Item Env:SEO_SITE_DIR
```

Для `seo:jekyll` потрібен запущений Docker Desktop. Команда використовує
офіційний локальний контейнер `ghcr.io/actions/jekyll-build-pages`, зафіксований
на digest `sha256:6791ebfd912185ed59bfb5fb102664fa872496b79f87ff8b9cfba292a7345041`:
Ruby 3.3.4, github-pages 232, Jekyll 3.10.0, Bundler 2.5.11, Gemfile.lock.
Це запуск контейнера на комп’ютері, не запуск workflow і не публікація.
Результат — `.private/seo-jekyll`, виключений із Git та Pages.

Альтернатива для встановлених Ruby/Bundler:

```sh
bundle install
bundle exec jekyll build --safe --destination .private/seo-jekyll
```

`seo:check` без записів заново обчислює всі результати та завершується
помилкою, якщо HTML, карта адрес, ілюстрації, sitemap або robots застаріли.
Посилання на змінені CSS/JS отримують SHA-256 версію в query, щоб кеш старого каталогу/коментарів не порушував нові маршрути. Повторна генерація перевірена на однаковий результат у цьому середовищі.
Помилки slug/articleId/мовних пар, відсутні Markdown/ілюстрації та конфлікти
шляхів зупиняють збірку. Дати не обчислюються з поточного часу. lastmod не
вигадується; наразі sitemap його не містить.

## Нова стаття

1. Оберіть один новий унікальний slug і наступний вільний сталий articleId.
   Не змінюйте ідентифікатори вже опублікованих матеріалів.
2. Покладіть два файли з однаковим іменем `<slug>.md` до
   `content/articles/uk/` та `content/articles/en/`. Заголовок H1 береться
   з JSON: не дублюйте його в Markdown. Збережіть погоджені джерела й підписи.
3. Оригінальні ілюстрації покладіть до відповідного мовного каталогу
   `content/articles/uk/image/` або `content/articles/en/image/`.
   Використовуйте неповторювані імена. У Markdown посилання можуть мати
   кореневий вигляд `/content/articles/uk/image/<name>.png`.
   Додайте змістовний погоджений alt; для підпису використовуйте figure/figcaption.
   Не замінюйте EN-ілюстрацію українською мовчки.
4. У двох JSON-каталогах додайте `slug`, `type: "article"`, `format: "text"`,
   наявну `category`, локалізовані `title`, `description`, `author`, фактичну
   `date`, відповідний `readTime`, `content: "<slug>.md"`, `featured`.
   `updated` — лише фактична редакція; `image` — погоджена обкладинка, якщо є.
5. У `firebase/article-map.json` додайте один `{id, slug, aliases: []}`
   для обох мов. Aliases додавайте лише для відомих старих посилань.
   Цей файл є джерелом сталого articleId, але **не** автоматичною зміною
   Firestore. Новий документ реєстру `articles/{id}` потребує окремого
   погодженого кроку за чинними правилами системи коментарів. Генератор
   не створює хмарних документів і не змінює Rules.
6. Виконайте команди перевірки вище. HTML, картки каталогу, дві останні
   картки головної, пошукова адреса, мовні зв’язки, карта legacy-адрес та
   sitemap формуються за джерелами автоматично.
7. Перегляньте обидві мовні сторінки, читання без JavaScript та мобільну
   ширину. Для локального перегляду зібраного сайту достатньо:

```powershell
python -m http.server 8133 --bind 127.0.0.1 --directory .private/seo-jekyll
```

Не запускайте експериментальні записи до реального Firebase під час
SEO-перевірки. Автоматичний браузерний тест цього пакета використовує
mock API; це не тест реальної Google Authentication.

## Старі посилання й помилки

Legacy query-шаблони не мають початкового noindex і не блокуються robots.
Вони містять статичні посилання на всі мовні статті; JavaScript за явною
картою переводить на новий маршрут. Це не HTTP 301. Зберігаються hash і
`commentsAdmin=1`, а невідомі параметри не стають цілями переходу.

Невідомий/порожній article-параметр після JS отримує нейтральну помилку й
noindex, без чужої статті або Article JSON-LD. Фізичний legacy-файл відповідає
HTTP 200. Без JavaScript query не може визначити серверний стан: доступний
нейтральний список статей. Новий відсутній каталог має справжній HTTP 404.
`includeInSitemap: false` означає виключення з sitemap, а не заборону обходу,
не автоматичний noindex і не висновок про індексацію Google.

## Відкат без Firestore

До публікації: повернути лише SEO-зміни в review-гілці; main не змінений.
Після окремо погодженої публікації: створити revert-коміт лише змін сайту,
перевірити legacy-адреси, потім опублікувати за чинним процесом Pages.
Rules, Auth, адміністраторів, settings і коментарі не відновлювати й не
перезаписувати: SEO-оновлення їх не змінює.

Якщо нові адреси вже поширені, не видаляйте їх під час відкату. Збережіть
десять готових HTML та потрібні assets/мінімальну адаптацію articleId, або
залиште на кожній новій адресі явний JS-перехід до її власної старої query-адреси
зі статичним посиланням без JS. Не допускайте циклу між legacy й новою
сторінкою: при варіанті JS-відкату вимкніть зворотний legacy-dispatcher.
Це не HTTP 301. Стабільні articleId і мовні відповідності залишаються чинними.
Не робіть git reset/force-push або відновлення всієї бази для відкату сайту.
